==================================================
GOAL
==================================================

Create a structured, versioned Intervention Catalog that maps each
diagnosed payment failure cause to the interventions that are valid
candidates for that cause.

The LLM MUST NOT be allowed to invent arbitrary interventions.

The Intervention Selection Engine will later receive candidates from
this catalog and rank them.

The Policy Engine will later decide whether a selected intervention
is ALLOWED, APPROVAL_REQUIRED, or REJECTED.

Therefore:

CATALOG ≠ SELECTION
CATALOG ≠ POLICY
CATALOG ≠ EXECUTION

The catalog only defines what interventions exist, what causes they
support, what prerequisites they have, and their static metadata.

==================================================
SUPPORTED CAUSES
==================================================

Use the existing diagnosis/cause naming conventions in the codebase.

The catalog must support these payment failure causes:

1. INSUFFICIENT_FUNDS
2. CREDIT_LIMIT_EXCEEDED
3. MANUAL_3DS_OTP_ABANDONMENT
4. ACQUIRER_PAYMENT_GATEWAY_TIMEOUT
5. ISSUING_BANK_OUTAGE
6. TECHNICAL_FAILURE
7. PAYMENT_INSTRUMENT_INVALID
8. TRANSACTION_LIMIT_EXCEEDED

If the current Validation module combines
INSUFFICIENT_FUNDS and CREDIT_LIMIT_EXCEEDED into one cause,
preserve the existing convention rather than breaking diagnosis.

Likewise, if existing cause enum names differ, reuse the existing
canonical names and create catalog mappings against those names.

DO NOT create duplicate cause enums.

==================================================
INTERVENTION METADATA
==================================================

Create a strongly typed InterventionDefinition.

At minimum it should contain:

- type
- name
- description
- supportedCauses
- priority
- estimatedCost
- expectedRecoveryProbability
- maxAttempts
- cooldownSeconds
- requiredCustomerData
- requiredMerchantConfig
- supportedChannels
- requiresPaymentLink
- requiresHumanApproval
- requiresResolutionCheck
- terminal
- enabled
- version

Do not encode dynamic merchant/customer policy rules into the
catalog.

For example:

maximum amount,
customer eligibility,
merchant-specific maximum attempts,
merchant-specific channel restrictions,
economic thresholds

belong to the future Policy / Boundary Engine.

The catalog only describes static intervention characteristics.

==================================================
CUSTOMER DATA REQUIREMENTS
==================================================

Define required customer data explicitly.

Examples:

SEND_EMAIL:

- email

SEND_SMS:
requiredCustomerData:
- phone

SEND_WHATSAPP:
requiredCustomerData:

SEND_PAYMENT_LINK:

CHANGE_PAYMENT_METHOD_PROMPT:

RETRY_PAYMENT:

- paymentAttemptId
- razorpayOrderId/payment provider identifiers as already available

HUMAN_REVIEW:
requiredMerchantConfig:
- humanReviewContact

Do not implement customer data collection in this task.
Only describe the requirements in the catalog.

==================================================
MERCHANT CONFIGURATION
==================================================

The future merchant configuration layer will determine which channels
a merchant allows.

The catalog should therefore NOT assume every merchant supports:

- email
- SMS
- WhatsApp

Instead, define requiredMerchantConfig metadata such as:

SEND_EMAIL:
- emailEnabled

SEND_SMS:
- smsEnabled

SEND_WHATSAPP:
- whatsappEnabled

HUMAN_REVIEW:
- humanReviewEnabled
- humanReviewContact

The future Intervention Selection layer will filter catalog
interventions against merchant capabilities before sending candidates
to the LLM.

==================================================
CATALOG API
==================================================

Create a clean catalog abstraction.

At minimum provide:

getInterventionsForCause(cause)

getIntervention(type)

getEligibleInterventionsForContext(context)

The first two functions should only perform catalog lookup.

The third function may perform static eligibility filtering based on:

- cause compatibility
- intervention enabled state
- required customer data
- merchant-enabled communication channels
- required merchant configuration
- required payment context

Do NOT implement dynamic Policy Engine rules here.

==================================================
ARCHITECTURAL RULE
==================================================

The final architecture must remain:

   ↓

   ↓

   ↓
Intervention Selection Engine
   ↓

The LLM will later rank catalog candidates.

The LLM MUST NOT be given permission to create arbitrary intervention
